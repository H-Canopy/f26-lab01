## 三、里程碑 1：诊断并修复失败的测试（30 分）

> **填写人：M2 `huangjiasheng567`**　分支 `fix/m1-root-cause`

### 3.1 失败测试的场景与期望

- **场景**：2 个房间（`roomA`、`roomB`）、2 个用户（Alice、Bob）、同一时间段 `[600,660)`。
  先在 A 房为 Alice 预订，再在 B 房为 Bob 预订同一时段。
- **期望**：第二次 `book(roomB, bob, [600,660))` 返回 `BookingResult.Confirmed`。
- **实际**：返回 `BookingResult.Waitlisted`（被误判为与 A 房的预订冲突）。
- **按核心不变式判断**：不变式的范围限定词是「**一个房间**」——两个不同房间在同一时段各有预订完全合法。
  因此期望结果合理，问题在系统实现，而非测试或不变式。

### 3.2 沿调用链逐层追踪（诊断记录表）

| 步骤 | 检查的文件 / 方法 | 观察到的事实 | 结论（排除 / 怀疑 / 确认） |
|---|---|---|---|
| 1 测试 | `BookingServiceTest.sameSlotInDifferentRoomsAreBothConfirmed` | 场景与期望值均符合不变式；`book` 的入参房间不同（A vs B） | **排除**：测试本身正确 |
| 2 服务层 | `BookingService.book` | 循环用 `store.bookingsForRoom(room)` 的返回值做 `overlaps` 冲突检查；若契约兑现，不会把 B 房误判为冲突 | **排除**：契约成立时逻辑正确 |
| 3 仓储接口 | `BookingStore.bookingsForRoom` 注释 | 承诺「The confirmed bookings held for `{@code room}`」（只返回该房间持有的已确认预订） | 契约定义明确 |
| 4 仓储实现 | `InMemoryBookingStore.bookingsForRoom` | 起始代码为 `return List.copyOf(bookings);` —— **返回全部预订，完全无视 `room` 参数**。对照：同类的 `waitlistForRoom` 却正确写了按房间过滤 | **确认**：契约在此被破坏（根因） |
| 5 领域层 | `TimeInterval.overlaps` | `start < other.end && other.start < end`，半开区间、首尾相接不重叠；`TimeIntervalTest` 5 个用例全过 | **排除**：冲突规则正确 |

**取证手段**（指导书允许任选，此处采用「直接针对下层写小测试」）：
回归测试 `bookingsForRoomReturnsOnlyBookingsForThatRoom` 直接向仓储放入 A、B 两房的预订，
断言 `store.bookingsForRoom(roomA)` 只返回 1 条且属于 A 房。
在未修复代码上运行得到 `expected: <1> but was: <2>` —— 证实 `bookingsForRoom` 把 B 房预订也返回了。

### 3.3 根因

- **根因所在的文件与方法**：
  `src/main/java/edu/cmu/cs214/booking/repo/InMemoryBookingStore.java` 的 `bookingsForRoom(Room)`。
- **为什么错了（契约层面）**：接口注释承诺「为该房间持有的已确认预订」，实现却 `return List.copyOf(bookings)`
  返回全部预订，**未按房间过滤** —— 契约在仓储实现这一层被破坏。
- **为什么报错位置 ≠ 出错位置**：断言失败发生在测试层，而 `BookingService.book` 完全信任该契约
  （这是分层架构的既定前提）。于是「不同房间同一时段」被误判为「同房间重叠」，本该确认的预订被放入候补。
  错误在上层「发作」，源头在下层。

### 3.4 修复

- **修改文件**：`InMemoryBookingStore.java`（+1 −2）
  ```java
  @Override
  public List<Booking> bookingsForRoom(Room room) {
      return bookings.stream().filter(b -> b.room().id().equals(room.id())).toList();
  }
  ```
- **commit**：`722b1c6`（[PR #2](https://github.com/H-Canopy/f26-lab01/pull/2) 已合并入 `main`）
- **为何落在根因所在的那一层**：在实现里兑现接口承诺，而不是在服务层加一个「只考虑同房间预订」的判断来绕开问题
  —— 后者虽能让失败测试通过，却会让其他依赖同一契约的调用者（现在的和将来的）继续受害。
- **与同类方法写法一致**：过滤写法与 `waitlistForRoom` 完全相同；`toList()` 保持原 `List.copyOf` 的不可变返回语义。
- **同一根因的其他受害者**：
  1. `BookingService.book` 的冲突检查 —— 本次失败测试即此症状；
  2. `BookingService.listBookings(room)` —— 会列出**所有房间**的预订（结果直接透传 `bookingsForRoom`）；
  3. 里程碑 2 新增的 `promoteFromWaitlist` —— 会拿**别的房间**的预订判定冲突，从而错误跳过本应晋升的候补者；
  4. M4 的 S6 测试（不跨房间晋升）—— 在本次修复之前必然失败。

  `waitlistForRoom` 的候补位置计算**不受影响**（起始代码已正确按房间过滤）。

### 3.5 正确性论证

- **全套测试为绿**：本修复与里程碑 2 的 `cancelBooking` 合并后，`mvn test` →
  `Tests run: 11, Failures: 0, Errors: 0, Skipped: 0`，`BUILD SUCCESS`
  （JDK 21.0.8 / Maven 3.9.16，由 M1 在合并前做集成验证）。
- **核心不变式仍然成立**：修复没有触碰 `BookingService.book` 的冲突判定逻辑，也没有触碰
  `TimeInterval.overlaps`；冲突检查现在只与**同房间**的已确认预订比较，因此
  「一个房间同时持有两个时间区间相互重叠的已确认预订」仍然不可能发生。
  既有用例 `bookWaitlistsWhenSlotIsTaken`、`backToBackBookingsAreConfirmed` 继续通过，从行为上印证不变式未被破坏。
- **回归测试**：`BookingServiceTest.bookingsForRoomReturnsOnlyBookingsForThatRoom`
  （**仅新增方法，未改动任何既有用例**）。
  修复前：`Tests run: 11, Failures: 2`（含 `expected: <1> but was: <2>`）；修复后：全绿。
- **完整诊断记录**（含取证与逐层推理）：[`docs/milestone1-diagnosis.md`](milestone1-diagnosis.md)
