## 三、里程碑 1：诊断并修复失败的测试（30 分）

> **填写人：M2 `huangjiasheng567`**　分支 `fix/m1-root-cause`

### 3.1 失败测试的场景与期望

- **场景**：2 个房间（`roomA`、`roomB`）、2 个用户（Alice、Bob）、同一时间段 `[600,660)`。
  先在 A 房为 Alice 预订，再在 B 房为 Bob 预订同一时段。
- **期望**：第二次 `book(roomB, bob, [600,660))` 返回 `BookingResult.Confirmed`。
- **实际**：返回 `BookingResult.Waitlisted`（被误判为与 A 房的预订冲突）。
- **按核心不变式判断**：不变式的范围限定词是「**一个房间**」——两个不同房间在同一时段各有预订完全合法。
  因此期望结果合理，问题在系统实现，而非测试或不变式。

### 3.2 沿调用链逐层追踪（诊断记录表）

| 步骤 | 检查的文件 / 方法 | 观察到的事实 | 结论（排除 / 怀疑 / 确认） |
|---|---|---|---|
| 1 测试 | `BookingServiceTest.sameSlotInDifferentRoomsAreBothConfirmed` | 场景与期望值均符合不变式；`book` 的入参房间不同（A vs B） | **排除**：测试本身正确 |
| 2 服务层 | `BookingService.book` | 循环用 `store.bookingsForRoom(room)` 的返回值做 `overlaps` 冲突检查；若契约兑现，不会把 B 房误判为冲突 | **排除**：契约成立时逻辑正确 |
| 3 仓储接口 | `BookingStore.bookingsForRoom` 注释 | 承诺「The confirmed bookings held for `{@code room}`」（只返回该房间持有的已确认预订） | 契约定义明确 |
| 4 仓储实现 | `InMemoryBookingStore.bookingsForRoom` | 起始代码为 `return List.copyOf(bookings);` —— **返回全部预订，完全无视 `room` 参数**。对照：同类的 `waitlistForRoom` 却正确写了按房间过滤 | **确认**：契约在此被破坏（根因） |
| 5 领域层 | `TimeInterval.overlaps` | `start < other.end && other.start < end`，半开区间、首尾相接不重叠；`TimeIntervalTest` 5 个用例全过 | **排除**：冲突规则正确 |

**取证手段**（指导书允许任选，此处采用「直接针对下层写小测试」）：
回归测试 `bookingsForRoomReturnsOnlyBookingsForThatRoom` 直接向仓储放入 A、B 两房的预订，
断言 `store.bookingsForRoom(roomA)` 只返回 1 条且属于 A 房。
在未修复代码上运行得到 `expected: <1> but was: <2>` —— 证实 `bookingsForRoom` 把 B 房预订也返回了。

### 3.3 根因

- **根因所在的文件与方法**：
  `src/main/java/edu/cmu/cs214/booking/repo/InMemoryBookingStore.java` 的 `bookingsForRoom(Room)`。
- **为什么错了（契约层面）**：接口注释承诺「为该房间持有的已确认预订」，实现却 `return List.copyOf(bookings)`
  返回全部预订，**未按房间过滤** —— 契约在仓储实现这一层被破坏。
- **为什么报错位置 ≠ 出错位置**：断言失败发生在测试层，而 `BookingService.book` 完全信任该契约
  （这是分层架构的既定前提）。于是「不同房间同一时段」被误判为「同房间重叠」，本该确认的预订被放入候补。
  错误在上层「发作」，源头在下层。

### 3.4 修复

- **修改文件**：`InMemoryBookingStore.java`（+1 −2）
  ```java
  @Override
  public List<Booking> bookingsForRoom(Room room) {
      return bookings.stream().filter(b -> b.room().id().equals(room.id())).toList();
  }
  ```
- **commit**：`722b1c6`（[PR #2](https://github.com/H-Canopy/f26-lab01/pull/2) 已合并入 `main`）
- **为何落在根因所在的那一层**：在实现里兑现接口承诺，而不是在服务层加一个「只考虑同房间预订」的判断来绕开问题
  —— 后者虽能让失败测试通过，却会让其他依赖同一契约的调用者（现在的和将来的）继续受害。
- **与同类方法写法一致**：过滤写法与 `waitlistForRoom` 完全相同；`toList()` 保持原 `List.copyOf` 的不可变返回语义。
- **同一根因的其他受害者**：
  1. `BookingService.book` 的冲突检查 —— 本次失败测试即此症状；
  2. `BookingService.listBookings(room)` —— 会列出**所有房间**的预订（结果直接透传 `bookingsForRoom`）；
  3. 里程碑 2 新增的 `promoteFromWaitlist` —— 会拿**别的房间**的预订判定冲突，从而错误跳过本应晋升的候补者；
  4. M4 的 S6 测试（不跨房间晋升）—— 在本次修复之前必然失败。

  `waitlistForRoom` 的候补位置计算**不受影响**（起始代码已正确按房间过滤）。

### 3.5 正确性论证

- **全套测试为绿**：本修复与里程碑 2 的 `cancelBooking` 合并后，`mvn test` →
  `Tests run: 11, Failures: 0, Errors: 0, Skipped: 0`，`BUILD SUCCESS`
  （JDK 21.0.8 / Maven 3.9.16，由 M1 在合并前做集成验证）。
- **核心不变式仍然成立**：修复没有触碰 `BookingService.book` 的冲突判定逻辑，也没有触碰
  `TimeInterval.overlaps`；冲突检查现在只与**同房间**的已确认预订比较，因此
  「一个房间同时持有两个时间区间相互重叠的已确认预订」仍然不可能发生。
  既有用例 `bookWaitlistsWhenSlotIsTaken`、`backToBackBookingsAreConfirmed` 继续通过，从行为上印证不变式未被破坏。
- **回归测试**：`BookingServiceTest.bookingsForRoomReturnsOnlyBookingsForThatRoom`
  （**仅新增方法，未改动任何既有用例**）。
  修复前：`Tests run: 11, Failures: 2`（含 `expected: <1> but was: <2>`）；修复后：全绿。
- **完整诊断记录**（含取证与逐层推理）：[`docs/milestone1-diagnosis.md`](milestone1-diagnosis.md)

### 4.1 需求拆解与测试场景设计（M4）

规则 R1~R6（摘自 `TASK.md`）：

| 规则 | 内容 |
|---|---|
| R1 | 方法签名：`public void cancelBooking(String bookingId)` |
| R2 | 删除 id 为 `bookingId` 的已确认预订，释放它占用的时段 |
| R3 | 如果不存在该 id 的预订，什么也不做（不抛异常，也不晋升任何人） |
| R4 | 删除后从该房间的候补名单中晋升：按 `seq` 先到先得，选第一个"区间不与任何剩余已确认预订重叠"的候补者，为其创建已确认预订，并删除其候补记录 |
| R5 | 每次取消至多晋升一人 |
| R6 | 晋升不得造成重叠：若最早的候补者仍与其他预订冲突，跳过他，考虑下一位；都不合适则不晋升任何人 |

场景与期望结果：

| 场景 | 操作 | 期望结果 |
|---|---|---|
| S1 基本取消 | Alice 订 A 房 [600,660)；取消它 | A 房**不再有任何**已确认预订（`bookingsForRoom(roomA)` 为空）；该时段被释放 |
| S2 无效 id | 有预订和候补者；取消一个不存在的 id | **状态完全不变**：A 房仍恰好 1 个已确认预订、候补名单仍 1 人；不抛异常、不晋升任何人（R3） |
| S3 晋升 | Alice 订 A 房 [600,660)；Bob 申请 [630,700) 进候补；取消 Alice | A 房恰好 1 个已确认预订，其 `user` 为 Bob、`interval` 为 `[630,700)`；A 房候补名单**变空**（Bob 的记录被删除） |
| S4 先到先得 + 至多一人 | Alice 订 [600,720)；Bob 候补 [600,660)（先），Carol 候补 [660,700)（后）；取消 Alice | 只晋升 `seq` 最早的 **Bob**（`[600,660)`）；**Carol 仍留在候补名单**（1 人）；A 房共 1 个已确认预订 —— 证明"至多晋升一人"（R5） |
| S5 跳过仍冲突者 | Alice 订 [600,660)，Dave 订 [700,760)；Bob 候补 [630,730)（先），Carol 候补 [610,650)（后）；取消 Alice | Dave 仍确认；Bob 因 `[630,730)` 仍与 Dave 重叠而被**跳过**、留在候补名单；**Carol** 被晋升 → A 房共 **2** 个已确认预订、候补名单剩 1 人（Bob）。此场景直接守护核心不变式（R6） |
| S6 不跨房间 | Alice 订 A 房；B 房有人候补；取消 Alice | A 房取消后为空；**B 房完全不变** —— Dave 仍确认、Bob 仍在 B 房候补，不被跨房间晋升 |

### 4.3 智能体提示词与计划审查（M3）

**第一轮提示词**（只要求计划、不写代码；M3 实际发出的原文）：

> 我需要在 `BookingService.java` 里实现 `cancelBooking(String bookingId)`。
> 要求：删除对应预订，找不到就什么都不做，删除后要按候补顺序（seq）晋升一个不冲突的人。
> 先给我计划，不要写代码。

**智能体给出的计划要点**：

1. 用 `store.findBooking(bookingId)` 查找，`Optional` 为空则 `return`（R3）
2. 取出被取消预订的 `room`，调用 `store.removeBooking(bookingId)` 删除（R2）
3. 调用 `store.waitlistForRoom(room)` 获取候补列表
4. 按 `seq` 排序后遍历，用 `TimeInterval.overlaps` 检查是否与剩余已确认预订冲突
5. 找到第一个不冲突者，创建新 `Booking`、删除候补记录、`break`（R5）

**审查计划时发现并要求智能体修改的问题（5 项）**：

| # | 智能体初版的问题 | M3 要求的修正 | 对应规则 |
|---|---|---|---|
| 1 | 冲突检查只与「被取消的那一个时间段」比较 | 必须与该房间**全部剩余已确认预订**逐一比较 | R6 |
| 2 | 依赖 `waitlistForRoom` 返回的列表顺序 | 必须显式 `sort(Comparator.comparingInt(WaitlistEntry::seq))`，不依赖存储层的偶然顺序 | R4 先到先得 |
| 3 | 建议调用 `book(room, user, interval)` 来「晋升」 | **拒绝**：`book()` 内部会检测冲突、可能再次加入候补，且消耗 `nextWaitlistSeq`；应直接 `new Booking(...)` + `store.addBooking(...)` | 副作用 |
| 4 | 找到合适者后仍继续遍历 | 加 `break`，严格遵守「至多晋升一人」 | R5 |
| 5 | 未确认候补名单是否按房间过滤 | 确认 `store.waitlistForRoom(room)` 已按房间过滤，不会跨房间晋升 | R4 不跨房间 |

修正后 M3 按该方案实现，**审阅 diff 后才接受**，并拆成 3 个小提交推送（见 §4.6）。

### 5.1 被审查的补丁

`changes/agent-attempt.patch` 新增的 `isAvailable` 方法：

```java
/**
 * Reports whether {@code room} is free over {@code interval}, so callers can
 * check availability before attempting to book.
 */
public boolean isAvailable(Room room, TimeInterval interval) {
    for (Booking b : store.bookingsForRoom(room)) {
        if (b.interval().start() >= interval.start()
                && b.interval().start() < interval.end()) {
            return false;
        }
    }
    return true;
}
```

### 5.2 逐种位置关系的判定表

设查询区间固定为 `Q = [600, 660)`：

| # | 位置关系 | 已有预订 E | 真实是否冲突 | 补丁的 `isAvailable` 返回 | 是否正确 |
|---|---|---|---|---|---|
| 1 | E 完全在 Q 之前 | [480,540) | 否（`600 < 540` 为假） | `true` | 正确 |
| 2 | E 在 Q 之前且首尾相接 | [540,600) | 否（`600 < 600` 为假，半开区间首尾相接不算重叠） | `true` | 正确 |
| 3 | E 先开始，延伸进 Q | [570,630) | **是**（`570<660` 且 `600<630`） | **`true`（漏判）** | **错误** |
| 4 | E 包含 Q | [540,720) | **是**（`540<660` 且 `600<720`） | **`true`（漏判）** | **错误** |
| 5 | E 被 Q 包含 | [610,640) | 是（`610<660` 且 `600<640`） | `false` | 正确 |
| 6 | E 在 Q 内开始，延伸出 Q | [630,720) | 是（`630<660` 且 `600<720`） | `false` | 正确 |
| 7 | E 与 Q 完全相同 | [600,660) | 是（`600<660` 且 `600<660`） | `false` | 正确 |
| 8 | E 在 Q 之后且首尾相接 | [660,720) | 否（`660<660` 为假） | `true` | 正确 |
| 9 | E 完全在 Q 之后 | [700,760) | 否（`700<660` 为假） | `true` | 正确 |

### 5.3 缺陷结论

- **被判错的是第 3、4 行**，位置关系分别是"E 先开始、延伸进 Q"和"E 包含 Q"。
- 这两类情形的共同点是 **E 的开始端点早于 Q 的开始端点**（`E.start() < Q.start()`），但区间仍与 Q 重叠。
- 补丁的条件是 `E.start() >= Q.start() && E.start() < Q.end()` —— **只检查已有预订的"开始"这一个端点**，
  因此永远漏掉"E 先于 Q 开始、却仍延伸进或覆盖 Q"的情形。
- **为什么违背不变式**：核心不变式是「一个房间永远不会同时持有两个时间区间相互重叠的已确认预订」。
  `isAvailable` 的语义是"这个区间能不能订"。第 3、4 行场景下补丁返回 `true`（声称可用），
  但实际调用 `book(...)` 会因冲突而返回 `Waitlisted`。调用者若信任该返回值，就会对"不可用"的时段做出错误判断
  —— 可用性判定与真实的冲突判定不一致，正是对"可用 ⇔ 无重叠"这一规则的破坏。
- **为什么它能通过所有现有测试**：现有测试（`TimeIntervalTest` 5 个 + `BookingServiceTest` 6 个）
  **没有任何一个调用 `isAvailable`**。新增方法对既有行为零影响，所以全部照常通过。
  "通过所有测试"只说明它**没有被测试覆盖**，不说明它正确 —— 典型的测试盲区掩盖缺陷。

| 4 | 为什么 `TimeInterval.overlaps` 应该是冲突规则的"唯一所在"？`agent-attempt.patch` 违背这一点带来了什么后果？ | M5 | `overlaps` 是"两个区间是否冲突"这条规则的**唯一实现**，连半开区间"首尾相接不算重叠"的语义也只定义在这里：集中一处 ⇒ 改规则只需改一处、所有调用者行为一致。而补丁自己重写了一遍条件，且**只检查 `E.start()` 这一个端点**，与 `overlaps` **不等价** —— 在第 3、4 类位置关系（E 先于 Q 开始却仍重叠、E 覆盖 Q）下漏判为"可用"。后果是系统里出现**两套互相矛盾的冲突判定**：`isAvailable` 说可用，`book` 却把请求放进候补。 |
| 5 | 一个补丁"通过了所有测试"，在什么情况下几乎没有任何意义？ | M5 | 当**被改动的代码路径没有任何测试覆盖**时，"通过所有测试"几乎没有任何意义。本实验就是现成例子：`isAvailable` 是新增方法，现有 11 个测试**无一调用它**，因此缺陷完全不可见。判断标准是：**把代码故意改坏，测试是否会变红** —— 不变红就说明覆盖是假的。本实验用"注释掉 `promoteFromWaitlist(room);`"验证晋升测试的鉴别力，用的正是这个手法。 |
| 6 | 本学期你将大量使用智能体写代码。结合本实验，谈谈你会如何分配"让智能体写"与"自己理解和验证"的时间。 | M4 | **答**：我会按「缺陷的可发现性」分配时间，而不是按代码行数。本实验给了两个方向相反的数据点：① `cancelBooking` 这类**行为边界写得很具体**的需求（R1~R6），智能体一次就写对了，我把时间花在审 diff 与写 S1~S6 测试上；② `isAvailable` 这类**看起来平淡**的方法，智能体生成的实现「通过了所有测试」却漏判两类位置关系 —— 而它能蒙混过关的唯一原因是**新方法没有任何测试覆盖**。所以我的准则是：先花时间把**契约与不变式写清楚**（本实验里 `BookingStore` 的接口注释、`ARCHITECTURE.md` 的「唯一规则所在」就是这种投入，它让 `bookingsForRoom` 的违约一眼可见）；再把时间投到**能变红的测试**上（本实验用「注释掉 `promoteFromWaitlist(room);`」验证鉴别力，只花 5 分钟，却区分了「真测试」与「装饰」）；最后才读生成代码，且只读**新增/修改的那几行 diff**。一句话：把时间从「读生成代码」挪到「定义规则 + 找反例」上收益高得多，但**审查 diff 一步都不能省** —— 缺陷恰恰藏在看起来合理的地方。　**（以下为原先记录的审题要点，保留备查）**：**要点**：反思题，须用本实验的真实经历支撑。可用素材：智能体一次就把 `cancelBooking` 写对了（R1~R6 全满足、3 个小提交），却在 `isAvailable` 上生成了"看起来合理、实际漏判两类位置关系"的实现；而里程碑 1 的预设缺陷同样是"实现与接口契约不一致"。可据此论证：**把时间花在明确契约与不变式、以及写"能变红的测试"上，比逐行阅读生成代码更划算；但审查 diff 不能省** —— 缺陷恰恰藏在看起来合理的地方。 |
